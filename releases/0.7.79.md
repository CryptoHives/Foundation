# CryptoHives Foundation 0.7.79

*Released 2026-11-21 · tag `0.7.79.59799`*

This release adds **.NET 11**. All packages ship a `net11.0` build, compiled with the new
**runtime-async** feature: the JIT compiles async methods itself instead of running the
state machines that Roslyn generates. In Cryptography, **`AesKeyWrapPad`** now uses the key wrap API
that `System.Security.Cryptography.Aes` gained in .NET 10 and .NET 11, and
**`Aes128/192/256.Create(key)`** creates an AES instance whose key is fixed for its lifetime.
The benchmarks move to .NET 11 and BenchmarkDotNet 0.16. The section
[Benchmarks: .NET 11 against .NET 10](#benchmarks-net-11-against-net-10) compares each platform
with the last .NET 10 runs.

---

### Known Issues

- **Threading.Analyzers needs the .NET 11 SDK.** The analyzer is now built against Roslyn 5.12,
  the compiler of the .NET 11 SDK. The .NET 10 SDK (10.0.404) ships Roslyn 5.9 and cannot load the
  analyzer. The build reports only warning CS9057 and still succeeds, but none of the CHT rules
  run, not even the CHT001 error. Build with the .NET 11 SDK, or keep Threading.Analyzers on 0.7.75
  until a later release references an older Roslyn (#362).
- **.NET 11.0.0 runtime-async: a `ValueTask` local can read `default`.** In code compiled with
  runtime-async, a `ValueTask` local is assigned from a method call, such as `Preserve()`, and
  awaited with `ConfigureAwait(…)`. After that await it reads `default`. This is a runtime bug, not
  a library bug. It breaks code that awaits a preserved `ValueTask` more than once. The two library
  tests that do this are skipped on runtime-async builds and pass with `/p:RuntimeAsync=false`.
  Code that awaits each `ValueTask` once, as the CHT rules require, is not affected.

## Highlights

### .NET 11 and runtime-async (#358)

- **New `net11.0` build** in every package. On .NET 11 it replaces the `net10.0` build. The other
  frameworks are unchanged: net462, net472 (Cryptography), netstandard2.0/2.1, net8.0 and net10.0.
- **Runtime-async.** The library's `net11.0` build is compiled with `runtime-async=on`. To build
  the classic state-machine form, pass `/p:RuntimeAsync=false`. Runtime-async builds define
  `RUNTIME_ASYNC`.
- **Package versions per target.** The `net11.0` build references the 11.x runtime packages. The
  other targets stay on the 10.x LTS line, because 11.x has no net8.0 assets: a net8.0 consumer
  would get the netstandard2.0 copies of in-box types such as `TimeProvider` (CS0433). Dependabot
  keeps each line on its major version (#359).
- **macOS** builds only `net11.0` by default.

### `AesKeyWrapPad` uses the BCL key wrap API (#358)

`AesKeyWrapPad` now has the same API as the key wrap methods of `System.Security.Cryptography.Aes`:
KWP (RFC 5649) arrived in .NET 10 and KW (RFC 3394) in .NET 11. Code moves between the two types
without renames.

- `EncryptKeyWrap`, `DecryptKeyWrap` and `TryDecryptKeyWrap`, the `…Padded` variants, and the
  static `GetKeyWrapLength` and `GetKeyWrapPaddedLength`. Overloads, argument checks, exact-length
  destinations and overlap rejection match the BCL.
- The span overloads do not allocate, unwrap runs in place, and a failed unwrap clears the
  destination. The KWP padding check is constant-time.
- New interop tests compare output and error behavior with the in-box implementation: KWP on
  net10.0 and later, KW on net11.0. The output is byte-identical.
- `AesKeyWrapBenchmark` gains OS rows. The managed implementation is about 1.7 to 4 times as fast
  as the in-box one, depending on the platform (see below).

### AES with a fixed key: `Aes128/192/256.Create(ReadOnlySpan<byte> key)` (#358)

`Create(key)` returns an instance whose key is fixed for its lifetime, as with the AEAD types such
as `AesGcm256.Create(key)`. After that, `Key`, `KeySize`, `GenerateKey` and `SetKey` throw
`CryptographicException`, so the key can be used but not read back or replaced. `Mode`, `Padding`
and `IV` can still be changed. A key of the wrong size throws. `Create()` keeps the settable
`SymmetricAlgorithm` behavior.

```csharp
using var aes = Aes256.Create(key);
aes.Mode = CipherMode.CTR;
aes.Padding = PaddingMode.None;
aes.IV = nonce;

byte[] ciphertext = aes.Encrypt(plaintext);
// aes.Key now throws CryptographicException
```

`SymmetricCipher.Dispose` now erases the key with `CryptographicOperations.ZeroMemory`, for every
instance, not only fixed-key ones.

## Breaking and behavior changes

> ⚠️ **`AesKeyWrapPad` method names.** `WrapKey`, `UnwrapKey`, `WrapKeyNoPad` and
> `UnwrapKeyNoPad` are removed. Use the BCL names instead: `EncryptKeyWrapPadded`,
> `DecryptKeyWrapPadded`, `EncryptKeyWrap` and `DecryptKeyWrap`. The output is unchanged.

> ℹ️ **.NET 11 consumers get the `net11.0` build**, compiled with runtime-async. Behavior is
> unchanged apart from the runtime issue under Known Issues.

## Benchmarks: .NET 11 against .NET 10

The .NET 11 runs are recorded on the `benchmarks` branch under `e9976f3a`. Each one is compared
with the last .NET 10 run on the same machine:

- **Cryptography:** 0.7.75 (`c41a1c61`). Since then only the AES key wrap code has changed.
- **Threading:** `7b697287`. The Threading code has not changed since then.

So the differences below come from the runtime, from runtime-async, and from the move to
BenchmarkDotNet 0.16.

Two effects appear on every platform. They are not regressions in the library:

- **Rows under about 2 ns rose by roughly 1 ns** for every library, including the raw
  `Interlocked.Increment` baseline. Examples are `AsyncAutoResetEvent.Set`,
  `AsyncManualResetEvent` set/reset and the uncontended CryptoHives `SpinLock`. The rise comes
  from BenchmarkDotNet 0.16's measurement floor, not from the code being measured.
- **Rows that return a `Task` (`AsTask`) are about 35–55% faster and allocate 56 bytes less** per
  operation. This comes from runtime-async.

### AMD Ryzen 5 7600X (Windows, AVX-512)

- **Cryptography:** unchanged overall. The in-box OS rows are about a tenth faster. A few rows
  moved at a single input size, such as AES-256-CCM at 128 KB and Camellia-128-CCM decrypt at
  1 KB. The neighbouring sizes did not move, so these rows are not taken as regressions. Scalar
  Poly1305 is about an eighth slower at 8 KB and larger, and faster on the Xeon.
- **Threading:** the library's rows are about a sixth faster overall. The largest gains are
  `AsyncConditionVariable` producer/consumer (about half the time), the `AsyncReaderWriterLock`
  writer and `AsyncManualResetEvent` set-then-wait.
- **Regressions:** `AsyncReaderWriterLock` reader with 100 waiters is about 15% slower.
  `AsyncBarrier` post-phase with a working action is slower, which shows only on this machine.

### Intel Xeon E-2136 (Windows, AVX2 without AVX-512)

- **Cryptography:** slightly faster overall.
  - ARIA, scalar AES-GCM and scalar Poly1305 are about a tenth faster.
  - SHA3-224 on AVX2 is a few percent slower at large inputs.
  - AES-GCM decrypt with AES-NI+PCLMUL is about 20% slower at 128 KB for all three key sizes, and
    at 8 KB for AES-192 and AES-256 but not AES-128. That pattern is not consistent, so it will be
    measured again before it is treated as a regression. Encrypt is unchanged.
- **Threading:** the library's rows are about a tenth faster overall. `AsyncConditionVariable` and
  the keyed locks show the largest gains.
- **Regressions:** none beyond the measurement floor described above.

### Apple M4 (macOS, Arm64)

- **Cryptography:** unchanged overall, except RIPEMD-160. The scalar RIPEMD-160 implementation is
  about 55% slower at every input size, while BouncyCastle's RIPEMD-160 is unchanged. That points to
  a change in Arm64 code generation in .NET 11 and will be investigated. The in-box SHA-2 rows
  (`OS Native`) now cost about 0.75 µs more per call. SHA-256 of 128 bytes takes about ten times as
  long as on .NET 10, while 128 KB is unchanged. So on .NET 11 the managed Arm64 SHA-256 is much
  faster than the in-box one for short inputs.
- **Threading:** the library's rows are about 7% faster overall. `AsyncConditionVariable`
  producer/consumer takes less than half the time.
- **Regressions:** the `ValueTask` waiter rows of `AsyncAutoResetEvent`, `AsyncManualResetEvent`
  and `AsyncLock` with 10 to 100 waiters are about 10–20% slower. ProtoPromise's matching rows are
  slower by a similar amount. On Windows the same rows are faster.

### AES key wrap, managed against in-box (.NET 11, 256-bit key)

| Platform | Wrap KW | Wrap KWP | Unwrap KW | Unwrap KWP |
|---|---|---|---|---|
| Ryzen 5 7600X | 503 / 874 ns | 628 / 1,272 ns | 549 / 1,100 ns | 638 / 1,359 ns |
| Xeon E-2136 | 681 / 2,240 ns | 846 / 2,747 ns | 679 / 2,745 ns | 860 / 2,937 ns |
| Apple M4 | 309 / 672 ns | 383 / 759 ns | 289 / 768 ns | 390 / 807 ns |

The first figure in each cell is CryptoHives and the second is the OS. The in-place unwrap makes
KWP unwrap about 8% faster than in 0.7.75. On Windows the OS KWP rows allocate, and the managed
rows do not.

## Benchmarks and infrastructure

- **Benchmarks on .NET 11 (#358).**
  - BenchmarkDotNet is now 0.16.0-preview.2, the first release with a net11.0 moniker.
  - `run-benchmarks.ps1` defaults to `-Framework net11.0 -Runtimes net11.0`. `-NoRuntimeAsync`
    reaches BenchmarkDotNet's child build as well.
- **Run configurations (#358).**
  - A run that differs in more than the framework is recorded as a run of its own:
    `classic-async`, `isa-<tier>`, `inprocess`.
  - The settings and the commit built are recorded in `run-config.json`. Recording files a run
    under the commit that was measured, even after `HEAD` has moved.
  - The trends dashboards can compare, for example, `net11.0` and `net11.0-classic-async` of one
    commit side by side.
  - `-LaunchCount <n>` averages a case over several processes.
  - The Threading reports show the Error and StdDev columns again.
- **CI.** `test-published-packages.yml` tests net11.0 and net10.0. The docs list net11.0 among the
  supported frameworks.
