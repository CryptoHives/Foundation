# CryptoHives Foundation 0.7.37

*Released 2026-09-30 · tag `0.7.37.24694`*

This release completes the NIST post-quantum trio. **ML-DSA (FIPS 204)** and **SLH-DSA
(FIPS 205)** join ML-KEM, and all three now have the FIPS pre-hash variants and the
PKCS#8 / SubjectPublicKeyInfo / PEM key formats. Every piece is fully managed and runs on every
target framework down to net462 and netstandard2.0. The hash side has substantial BLAKE3 and
BLAKE2 kernel work, and the threading package gains two new primitives and non-blocking `Try*`
acquisition.

One change removes public API: `Blake3.TryHashOneShot` is no longer public. Two narrower changes
are listed with it under **Breaking and behavior changes** below: code that imports both this
package's namespace and `System.Security.Cryptography` may need an alias, and the default SIMD tier
for BLAKE2 has changed.

---

## Highlights

### ML-DSA-44/65/87 — post-quantum signatures (#178)

This is FIPS 204 KeyGen, Sign and Verify, including the rejection loop. Signing is hedged by
default, and context strings are supported. The math layer is `int`-based (q = 8380417) and is
independent of ML-KEM's by design.

Two API levels ship, as they do for ML-KEM:

- **`MLDsa` / `MLDsaAlgorithm`**: a key-holding class that mirrors .NET 10's
  `System.Security.Cryptography.MLDsa` member for member, so porting from it means changing only
  the `using`. `Dispose()` zeroizes the retained seed and private key.
- **`MLDsa44/65/87`**: a stateless, span-based `IDsa` for protocol code that owns its own key
  bytes.

```csharp
using var signer = MLDsa.GenerateKey(MLDsaAlgorithm.MLDsa65);
byte[] signature = signer.SignData(message, context);

using var verifier = MLDsa.ImportMLDsaPublicKey(MLDsaAlgorithm.MLDsa65, signer.ExportMLDsaPublicKey());
bool valid = verifier.VerifyData(message, signature, context);
```

`MLDsa.IsSupported` is always `true`. The implementation never depends on Windows CNG or OpenSSL.

**Hardening:** infinity-norm checks run in constant time with no early exit, rounding and hint
arithmetic is branch-free, secrets are zeroized on every loop iteration, and hint encodings are
strictly validated for strong unforgeability.

`GenerateKey` and `ImportMLDsaPrivateSeed` accept `pairwiseConsistencyTest: false`, as ML-KEM's do.
The check performs a full signature, so it costs more here than it does for ML-KEM. Skipping it
never changes the key that is produced.

**Conformance:** the complete runnable NIST ACVP set (keyGen, deterministic and hedged sigGen, and
sigVer including the modified commitment/z/hint/message cases). Every case runs through both
`IDsa` and `MLDsa`. The vectors are stored in NIST's own ACVP JSON schema. Interop is checked
against BouncyCastle and against .NET 10 `MLDsa`, including byte-identical keys from the same
seed.

### SLH-DSA — all 12 parameter sets (#179)

This is FIPS 205 in both instantiations:

- **SHAKE256**
- **SHA-2**: compressed ADRS, MGF1-based H_msg, HMAC-based PRF_msg, and the SHA-512 split for
  security categories 3 and 5.

WOTS+, XMSS, the hypertree and FORS are hash plumbing over the existing SHA-2 and SHAKE cores.
No new number theory was needed.

`SlhDsa` and `SlhDsaAlgorithm` mirror .NET 10's `System.Security.Cryptography.SlhDsa` member for
member. `SlhDsaApiTests.ApiSurface_MatchesTheInBoxType` compiles the same source against both types,
so any drift breaks the build rather than a test run. The difference that matters in practice is
`IsSupported`: the in-box type reports `false` on Windows 11 25H2, while this package works on any
platform.

**Choose the `f` sets for general use.** The `s` sets sign slowly by design, at roughly 10⁶ hash
invocations per signature. If throughput matters, ML-DSA is the better fit.

There are deliberately no per-set `IDsa` wrappers. `IDsa` takes one 32-byte seed, while FIPS 205
key generation takes three n-byte seeds.

**Conformance:** SLH-DSA signatures are 7.8–49 KB each, so the complete runnable ACVP set is
11.8 MB gzipped. Instead, a stratified, rule-based selection is committed:

- every keyGen case;
- one deterministic and one hedged sigGen per set;
- one valid sigVer per set, plus the full failure matrix on four representative sets.

`scripts/fetch-slhdsa-acvp-vectors.py --profile full` fetches the complete set, which the tests
then use automatically. The new weekly `acvp-full-vectors` workflow runs the full set on CI.

### HashML-DSA and HashSLH-DSA pre-hash variants (#180)

`SignPreHash` and `VerifyPreHash` are available on both `MLDsa` and `SlhDsa`, in all four overload
shapes the .NET 10 types define. The caller computes the digest PH(M) and passes it together with
its OID. The OID is bound into the signed prefix, so a pre-hash signature and a pure signature over
the same message are never interchangeable. `PreHash.cs` holds the twelve approved functions
(SHA-2, SHA-3, SHAKE128/256) and rejects unapproved OIDs and wrong digest lengths.

> **One hazard is inherited from the in-box shape.** The span overload of `SignPreHash` takes the
> **destination** as its second argument, whereas `SignData(byte[], byte[])` takes the **context**
> there. Passing two arrays to the wrong method compiles and silently does something else.

Both conformance files contain every pre-hash function and every parameter set. PH(M) is recomputed
from each vector's message with this library's own hash implementations, so the OID-to-hash binding
is tested end to end. Interop is checked in both directions against BouncyCastle's
`HashMLDsaSigner` and `HashSlhDsaSigner`.

### PKCS#8, SubjectPublicKeyInfo and PEM for all three PQC types (#293)

The key-format block that 0.6.101 listed as *"not implemented, and deliberately so"* has now
landed. It is implemented once, in `KeyFormats/`, and `MLKem`, `MLDsa` and `SlhDsa` forward to it.
All DER goes through `System.Formats.Asn1`, and no ASN.1 is hand-rolled.

- **ML-KEM and ML-DSA private keys** write the seed arm of the
  `CHOICE { seed, expandedKey, both }` when the key retains its seed, and the expanded arm
  otherwise. The output is byte-identical to .NET 10. SLH-DSA has no seed and no CHOICE.
- **Encrypted PKCS#8** writes PBES2 only (PBKDF2 with AES-CBC). It can also *read* the legacy
  PKCS#12 schemes that older OpenSSL and Windows wrote.
- **`PbeOptions`** takes the place of the in-box `PbeParameters`. `PbeParameters` does not exist
  below netstandard2.1, and declaring it here would collide with `Microsoft.Bcl.Cryptography`.

```csharp
string spki = key.ExportSubjectPublicKeyInfoPem();
string encrypted = key.ExportEncryptedPkcs8PrivateKeyPem(
    password,                                              // ReadOnlySpan<char> or ReadOnlySpan<byte>
    new PbeOptions(PbeEncryptionAlgorithm.Aes256Cbc, Pbkdf2Prf.HmacSha256, 600_000));
```

**Secrets go through erasable memory only.** No public member takes a password as a `string` or
returns a plaintext private key as a `string`. A `string` cannot be overwritten, so a secret stored
in one stays on the heap until the collector happens to reuse that memory.

- Passwords are `ReadOnlySpan<char>` or `ReadOnlySpan<byte>`.
- The plaintext PEM export is `TryExportPkcs8PrivateKeyPem(Span<char>, out int)`, sized by
  `GetPkcs8PrivateKeyPemSize()`.

The in-box PQC types' `string` overloads were added only for convenience on downlevel platforms,
which are exactly the platforms this library targets, so this library declines them on purpose.
The porting table is in `erasable-memory.md`.

### `CryptographicOperations.ZeroMemory` and `FixedTimeEquals` are public

These are available on all six target frameworks, with `char` overloads that the in-box type lacks
on every .NET version. Use `ZeroMemory` to erase any secret buffer, and `FixedTimeEquals` for any
MAC or tag comparison. The in-box type does not exist below netstandard2.1, which meant the
`mac-algorithms.md` sample did not compile on net462, net472 or netstandard2.0.

### BLAKE3 kernel work (#295, #296, #306)

- **Two chunks** get their own AVX2 pair kernel: the row-oriented SSSE3 kernel widened to
  256 bits, with no transpose.
- **Direct 32-byte root.** A digest of at most 32 bytes skips the full output-block squeeze and
  its staging.
- **Wide XOF tail.** A squeeze of 2–7 remaining blocks uses the wide kernel instead of running
  block by block.
- **Deferred subtree halves.** An input that ends on an aligned batch or group boundary is reduced
  to two halves by the wide parent kernels rather than committed chunk by chunk.
- **Stepped rounds on every tier.** A fixed 16-chunk AVX-512 kernel reads its rows straight from
  the input. On AVX-512VL hardware, rotates use `vprold`. On NEON, the rotate by 16 is a halfword
  swap.
- **Direct absorb.** Whole blocks of a new chunk are compressed straight from the input instead of
  being buffered.

The package stays **single-threaded by design**, because a `HashAlgorithm` that quietly occupies
thread-pool threads is surprising in a library. The benchmark pages therefore show a
`Blake3.Managed (1 thread)` row next to the multi-threaded one.

Where it stands: up to a few kilobytes this implementation is level with or ahead of the
single-threaded libraries it is benchmarked against; on large single-threaded inputs the native Rust
binding keeps a small lead.

**Credit.** Several of these changes were prompted by comparing against the
[BLAKE3 reference implementation](https://github.com/BLAKE3-team/BLAKE3) and
[Blake3.Managed](https://github.com/Dissimilis/Blake3.Managed), including Blake3.Managed's published
performance write-up. The phase-interleaved "stepped" rounds follow the layout the reference C code
uses and Blake3.Managed documents for RyuJIT. The new ideas were reimplemented in our codebase
and kept only where our own benchmarks confirmed them.

### BLAKE2 picks up what BLAKE3 taught (#296)

- **BLAKE2s SIMD leaves `EXPERIMENTAL`.** The public BLAKE2s previously ran scalar-only, and it now
  defaults to SSSE3.
- **Shorter dependency chain.** The message add is associated as `(a + m) + b`, and the
  diagonalization leaves the most recently written row in place.
- **AVX-512VL rotates**, and masks and IVs come from the constant pool.
- **One-shot `TryComputeHash`** overrides for both BLAKE2 variants.
- **Shared code.** BLAKE2s drives its SSSE3 kernel from BLAKE3's G round instead of keeping a copy
  that had drifted.

## Threading

### Two new primitives

- **`AsyncExchange<T>`** is a two-party rendezvous, the async counterpart of Java's
  `Exchanger<V>`: each side hands over a value and receives the other's (#250).
- **`AsyncConditionVariable`** means "wait until a condition holds" and is paired with an
  `AsyncLock`. Signals are not stored, so a notify with no waiter is lost by design (#250).

### Non-blocking acquisition (#283)

Every primitive gains a `Try*` member that acquires only if it can do so immediately, without
arming a zero timeout: `TryLock`, `TryReaderLock`, `TryWriterLock`, `TryUpgradeableReaderLock`,
`TryUpgradeToWriterLock`, `TryWait` and `TryExchange`. When one returns `false`, do other work and
ignore the default `Releaser`.

### Tests and benchmarks

- **DotNext.Threading is now a benchmark competitor** for the six primitives with a direct
  equivalent: `AsyncLock`, `AsyncManualResetEvent`, `AsyncAutoResetEvent`, `AsyncCountdownEvent`,
  `AsyncBarrier` and `AsyncReaderWriterLock` (#284, #285). It runs on net10.0 only.
- The threading tests are reorganised into namespaces and folders per primitive, as the set of
  primitives keeps growing (#282).

## Bug fixes and performance

### Cryptography

- **The BLAKE2b default selected NEON on AArch64**, which is the kernel its own comment said must
  not be chosen because it measures slower than scalar. `WithImplicit()` derived `Neon` back from
  `All & ~Neon`. The default is now `SimdSupport.Avx2`, which `WithImplicit()` cannot undo. Nothing
  changes on x86.
- **The BLAKE2s AVX2 kernel was unreachable.** AVX2 implies SSSE3, and the dispatcher tested SSSE3
  first. Dispatch now tries the widest tier first.
- **SIMD flag handling (#301).** Every tier is gated on `IsSupported`, so the JIT drops branches
  that cannot run on the current machine (for example, no Arm path on x86). `WithImplicit()` sets
  the instruction sets a CPU implies. Arm paths that assume little-endian are now gated on it.
- **Short final blocks are assembled in registers (#302).** Staging a partial block through a
  zeroed buffer stalled on store-to-load forwarding. The new `BinaryLoad` helpers build the value
  directly. This is used in Poly1305, GCM (GHASH and AES-NI tails) and AES-CMAC.
- **`HashAlgorithmPool`** used to send every `ReadOnlySequence` through `AppendData`, which
  bypassed the one-shot path. Single-segment sequences now call `TryComputeHash` directly. Pooled
  instances are also no longer reset twice (#300).
- **`SHA1` and `AsconXof128`** gained the `ReadOnlySequence` static helpers that every other hash
  type already had (#300).

## New features

- **`HashAlgorithm.TryComputeHash` is now `virtual` (#300).** An algorithm with a faster
  single-call path can override it. The contract is in the XML docs: an override must keep the
  auto-reset behavior, and it must still honour data already appended, falling back to `base` when
  it needs a fresh state. As a result, a `Blake3` held as a `HashAlgorithm` now reaches the one-shot
  path, which previously only the benchmark did.

## Breaking and behavior changes

> ⚠️ **`Blake3.TryHashOneShot` is now `internal`.** It was public in 0.6.101. It has a precondition
> the type system cannot express: the instance must be freshly initialized, and calling it
> mid-stream *silently produces the wrong digest*. Use `TryComputeHash`, `Blake3.TryHashData` or
> `Blake3.HashData` instead. All three reach the same fast path and establish the precondition for
> you.

> ℹ️ **`CryptographicOperations` and `PbeEncryptionAlgorithm` are now public in
> `CryptoHives.Foundation.Security.Cryptography`.** This is source-only and narrow: a file that
> imports both that namespace and `System.Security.Cryptography` *and* uses either name gets
> **CS0104** (ambiguous reference). Fix it on the consumer side with
> `using Bcl = System.Security.Cryptography;`. The types are
> deliberately *not* declared in the `System` namespace: on the downlevel targets that would be a
> hard CS0433 collision with `Microsoft.Bcl.Cryptography`, which no alias can fix.

> ⚠️ **Default SIMD selection changed for BLAKE2.** BLAKE2s now runs SSSE3 instead of scalar, and
> BLAKE2b on AArch64 runs scalar instead of NEON. Digests are unchanged; only speed differs.

## Measured and rejected

Recorded so the questions stay settled.

- **Rolling rounds 2–7 of the wide BLAKE3 kernels into a loop.** On an AVX2-only CPU with 16
  vector registers this was substantially slower, because the renamed message words live across the
  loop's back edge and spill. On AVX-512 it was slightly slower in every variant tried. The
  row-oriented 128-bit kernels do loop, and lose nothing by it.
- **Routing two BLAKE3 chunks through the 8-lane kernel.** Duplicating six of eight lanes wastes
  more than it saves, so the pair kernel stays.
- **Batching a 1–15-chunk AVX-512 tail.** From eleven chunks up, two runs of identical code
  disagreed by more than the difference being measured, so the kernel is not carried.
- **BLAKE2 on NEON.** Measured on an Apple M4, it is slower than scalar for both variants at every
  size. That confirms the gating decisions on real hardware. BLAKE3's NEON kernel, which uses the
  wide-register approach, runs close to the Rust native binding.
- **Also tried and dropped:** an all-registers partial kernel, a fixed-4 SSSE3 kernel, and
  constant-folding the digest copy.

## Benchmarks and infrastructure

### Stable benchmark runs on Windows

Benchmark results on the Windows machine (AMD Ryzen 5 7600X) used to **differ noticeably between
runs of unchanged code**. The root cause is thermal. Modern CPUs adjust their boost clock
quickly as they heat up, so a run that started on a hot CPU ran at a lower clock than one that
started cool. Four changes now make runs consistent:

- **Maximum processor state set to 99%** in the High Performance power plan that the benchmarks
  switch to. This effectively disables the top boost clock; AMD Ryzen Master then showed the CPU
  running noticeably cooler at a steady clock.
- **Pinning to the cores Windows prefers (4, 6, 8 and 10)** with `run-benchmarks.ps1 -PinToCore`,
  so a benchmark cannot land on CPU 0, which also services interrupts.
- **A reboot before every run**, with OneDrive and other background services closed.
- **Optional cool-down** between benchmark cases with `-CooldownSeconds`, so every case starts from
  a similar thermal state.

Recorded Windows runs are now far more consistent. **The macOS (Apple M4) runs are still in
progress**, and those dashboards will follow.

### Tooling

- `run-benchmarks.ps1 -DisableIsa` masks CoreCLR instruction-set support, so one host can measure
  every SIMD tier (#300).
- Benchmark sizes are split per algorithm family, and the NUnit fixtures take their sizes from the
  same source that BenchmarkDotNet uses (#296, #300).
- `HashAlgorithmAdapter` puts every in-box and third-party hash behind the same virtual
  `TryComputeHash`. This replaces the per-call type checks (#300).
- ML-DSA and SLH-DSA join the benchmark registry and the trends dashboard, with pre-hash rows next
  to their pure counterparts (#178, #179, #180).
- New weekly workflows run the full ACVP vector sets and check for vulnerable transitive
  packages (#282).
- Build housekeeping: strong-name signing and warnings (#281), and a fix for the netstandard test
  build (#310).
