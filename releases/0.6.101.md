# CryptoHives Foundation 0.6.101

*Released 2026-09-01 · tag `0.6.101.TBD`*

This release adds **ML-KEM (FIPS 203)**, the first post-quantum algorithm in the cryptography
package, and reworks the Memory package around pooling and payload lifetime. It also fixes a
key-material leak in KMAC and a 20–45% scalar-path throughput regression across four cipher
families.

Several behavior changes are listed under **Breaking and behavior changes** below — the Memory chunk
budgets in particular now mean something different for every `T` except `byte`. Please read that
section before upgrading.

---

## Highlights

### ML-KEM 512/768/1024 — post-quantum key encapsulation (#177)

FIPS 203, fully managed, running on every target framework down to net462 and netstandard2.0. K-PKE
and ML-KEM KeyGen/Encaps/Decaps are built on the existing SHA-3/SHAKE Keccak core, with
Montgomery/Barrett NTT arithmetic.

Two API levels ship:

- **`MLKem` / `MLKemAlgorithm`** — a key-holding class that deliberately carries the same names and
  signatures as .NET 10's `System.Security.Cryptography.MLKem`, so porting from the in-box type is a
  `using` swap and nothing else. `Dispose()` zeroizes the retained seed and decapsulation key.
- **`MlKem512/768/1024`** — a stateless span-based `IKem` for protocol code that owns its key bytes.

```csharp
using var receiver = MLKem.GenerateKey(MLKemAlgorithm.MLKem768);
byte[] ek = receiver.ExportEncapsulationKey();

using var sender = MLKem.ImportEncapsulationKey(MLKemAlgorithm.MLKem768, ek);
sender.Encapsulate(out byte[] ciphertext, out byte[] senderSecret);

byte[] receiverSecret = receiver.Decapsulate(ciphertext);   // == senderSecret
```

`MLKem.IsSupported` is always `true` here — it never depends on Windows CNG or OpenSSL.

**Not implemented, and deliberately so:** the PKCS#8/SPKI/PEM import and export members. If a port
needs those, keep the in-box `MLKem` for that path or store the raw 64-byte seed. Do not hand-roll
the ASN.1.

**Conformance.** The curated vector set — 2 keyGen and 2 encaps per parameter set — was replaced with
the full NIST ACVP-Server set: 240 cases across 75 keyGen, 75 encapsulation, 30 decapsulation and 60
key checks, taking `MLKemAcvpTests` from 42 cases to 555. The vectors moved out of C# literals into
an embedded pipe-delimited, gzipped data file; ML-KEM-1024 alone carries ~9.6 KB of hex per keyGen
case, which inline would *be* the test source rather than live in it. Pipe-delimited rather than JSON
so it parses with `String.Split` on net48 without another package reference.

### Memory: pooled writers, and payloads that outlive their producer (#277)

`ArrayPoolBufferWriter<T>` was already pooling its buffers; now the writer object itself is recycled.
It implements `IResettable` and returns itself on `Dispose`.

The more consequential addition is **`SequenceLease<T>`** — a `readonly struct` carrying a
`ReadOnlySequence<T>` together with the `IDisposable` that owns it. Data can leave the scope that
built it without a copy and, measured, **without an allocation**:

```csharp
static SequenceLease<byte> BuildPayload()
{
    var writer = ObjectPools.RentBufferWriter<byte>();   // deliberately not `using`
    Serialize(writer);
    return writer.LeaseSequence();                       // the writer rides along
}

using SequenceLease<byte> payload = BuildPayload();
var reader = new Utf8JsonReader(payload.Sequence);       // read in place, no copy
```

| pattern | 1 segment | 4 segments | 16 segments |
|---|---|---|---|
| borrow (producer held) | 56 B | 224 B | 280 B |
| **lease (payload escapes)** | **56 B** | **224 B** | **280 B** |
| lease boxed to `ISequenceOwner<T>` | 104 B | 272 B | 328 B |

Boxing costs a measured +48 B, so the "do not cast it to the interface" guidance is quantified rather
than asserted — the same bargain `ObjectOwner<T>` already strikes.

**Settings now apply when a writer is rented, not when it is constructed.** That was the wrong axis
to shard a pool on: pools multiplied with use cases, each with its own miss rate. A single pool per
`T` now serves the whole application, and `ArrayPoolBufferWriterProvider<T>` holds one immutable
profile per use case:

```csharp
static readonly ArrayPoolBufferWriterProvider<byte> JsonWriters   = new(maxChunkBytes: 1 << 20);
static readonly ArrayPoolBufferWriterProvider<byte> SecretWriters = new(clearArray: true);
```

`PoolFactory` becomes public with a general `CreatePool<T>(create, reset)`, so callers can pool types
this package does not reference — `Utf8JsonWriter` being the motivating case. **No `System.Text.Json`
dependency was added**, verified across all six target frameworks; Memory still has exactly one
non-shim dependency.

**Also joining `ISegmentOwner<T>`:** `ISequenceOwner<T>` with `SegmentSequence<T>` and
`EmptySequence<T>`, so every segment strategy becomes a sequence owner for free.

### Two allocation bugs, found by the pooling work

- **`ArrayPoolBufferWriter<T>.Dispose` leaked a rented array.** It walked the segment chain but never
  the in-progress buffer, so a writer torn down between `GetSpan` and the next segment boundary lost
  that buffer to the pool permanently. Pooling would have amplified this on every cycle. Both paths
  now share a single release routine.
- **A double `Dispose` poisoned a pooled writer.** The second call found the pool reference already
  cleared, fell through, and marked an instance *sitting in the pool* as disposed. The next renter
  threw `ObjectDisposedException` on its first `GetSpan`.

## Security

### KMAC left the MAC key in the shared array pool (#278)

`KeccakKMacCore.AbsorbKeyPad` assembles `bytepad(encode_string(K), rate)`. When that exceeds the
rate — a key longer than **168 bytes for KMAC128** or **136 for KMAC256** — it built the result in a
buffer rented from `ArrayPool<byte>.Shared` and returned it **without clearing**. The buffer holds
the raw MAC key, so the next caller to rent that bucket could read it. Shorter keys take the
`stackalloc` path and were never affected.

The class was otherwise careful — `Dispose` already cleared the encoded key — so only the transient
copy escaped. Every other pooled return in the Keccak, cSHAKE and KT code already cleared, which is
why this reads as an oversight rather than a decision.

Two further returns now clear for uniformity: KMAC's function-name and customization strings, and
GCM's padded nonce. Both carry public data, so this buys no secrecy — only the absence of a reader
wondering why those two differed. **No unguarded `ArrayPool` return remains in the package.**

`ArrayPoolMemoryStream` and `PooledSegment<T>.Rent` gained the `clearArray` option that
`ArrayPoolBufferWriter<T>` already had, so a caller holding key material can ask for zeroing on every
pooled type rather than three out of four. On the stream it is honoured on both release paths —
disposal, and the buffers a `SetLength` truncation drops.

## Bug fixes

### Cryptography

- **Scalar-path throughput regression of 20–45% across AES, ARIA, Kalyna and BLAKE2b (#266).**
  `AesCore`'s `SBox`/`InvSBox`/`Rcon`, `AriaCore`'s `SB1`–`SB4`, `KalynaCore`'s `S0`–`S3` and
  `Blake2bState`'s `IV` were computed `ReadOnlySpan<T>` properties rather than plain arrays. Combined
  with `AggressiveOptimization` on their hot-path callers, the JIT could not prove two calls returned
  the same span identity, so it could not share bounds checks across repeated lookups within a
  method. This hit AES-CBC/GCM/CCM scalar throughput hardest.
- **Camellia regression (#271).** A hot path grew past the inlining budget because of the
  `GetArrayReference` shim.
- **Kuznyechik was very slow (#258).** Substantial performance work.
- **Keccak built its SIMD tables even when unused (#269).** Now built on demand. Not critical — the
  NuGet packages compile those paths out, because they are consistently slower than scalar Keccak.

### Performance

- **BLAKE3 gains SSSE3-specific special cases, and its IV initialization becomes a `const` vector**
  rather than a static readonly, so it can contribute to the one-shot fast path (#270).
- **AES-GCM on NEON improves for large blocks** (#270).
- **SIMD defaults were refactored** so release and debug builds both select the best available
  implementation by default (#270).

## Breaking and behavior changes

> ⚠️ **`ArrayPoolBufferWriter<T>` chunk budgets are now bytes, not element counts.**
> `DefaultChunkSize`/`MaxChunkSize` become `DefaultChunkBytes`/`MaxChunkBytes`, and the writer
> divides by `sizeof(T)` to decide how many elements fit. The old element counts put every `T` wider
> than a byte straight onto the large object heap — 256 KiB for `int`, 1 MiB for `Guid`. **For `byte`
> the two units coincide and behavior is unchanged.** For any other `T`, a caller passing explicit
> sizes is now passing a different quantity.
>
> 64 KiB is the ceiling because `ArrayPool` serves from buckets of `16 × 2ⁿ` elements, rounding up,
> and the bucket above 65,536 bytes is 131,072 with nothing between — so it is the largest budget
> whose array is guaranteed to stay off the LOH.

> ⚠️ **`DefaultChunkSize` and `MaxChunkSize` were `public static readonly int` and are now `const`,**
> so they can serve as optional-parameter defaults. This is binary breaking for anything compiled
> against 0.6.79: that code emits `ldsfld`, and against a `const` there is no field to load. Source
> compatible after the rename above.

> ⚠️ **A disposed `AsconAead128` now throws `ObjectDisposedException`** where it previously kept
> working. Its key lived in `readonly ulong` fields, so `Dispose` could not clear anything; the
> fields are now zeroed. Zeroing alone would have turned a use-after-dispose from "works" into
> "silently encrypts under an all-zero key", so the operations refuse instead — matching `AesGcm`,
> `AesCcm` and both ChaCha types, which already did.

## Measured and rejected

Recorded so the questions stay settled.

**Pooling `ArrayPoolBufferSegment<T>`** — the last per-payload allocation on the writer path, at 56
bytes per segment. The decision rule was set before measuring: under 3% wall-clock improvement, do
not pool. Every configuration measured **negative** — pooling those segments is 1.8× to 2.8× *slower*
than allocating them, including with a `[ThreadStatic]` free list carrying no synchronisation at all,
tested precisely so the result could not be blamed on `DefaultObjectPool` overhead.

Gen0 collections drop from 21 to 0, which confirms the mechanism rather than contradicting it: the
garbage really is eliminated, and it does not matter, because Gen0 cost scales with *survivors* and
these segments have none. No library code changed; the prototype was standalone and is discarded.

**Caching the stream's rebuilt segment chain** — `ArrayPoolMemoryStream.GetReadOnlySequence()`
measured ~500–1100 ns on a 16-buffer stream, rebuilding each call. Also not recommended: the cost
avoided is allocation, which the above shows is cheap; the common write-once-read-once path pays the
build exactly once either way; and the invalidation discipline spans six mutating sites, where
missing one hands back a sequence describing the wrong content.

## Documentation

- **Both porting guides and the Memory README were brought up to the shipped API.** The worst of the
  drift was the `ArrayPoolBufferWriter` constructor, listed by parameter names that no longer
  compile. Two rules were stale in a way that mattered more than a rename: *"never return the
  sequence to a caller that outlives the `using`"* was right when copying was the only alternative,
  and `PooledSegment<T>` was described as clearing "in DEBUG builds automatically" — which invites
  verifying a wipe in Debug and shipping a Release build that never asked for one.
- **New pages** for `ISequenceOwner<T>`, `SequenceLease<T>`, `SegmentSequence<T>`,
  `EmptySequence<T>`, `ArrayPoolBufferWriterProvider<T>` and `PoolFactory`, plus revisions across the
  Memory package documentation.
- **The Memory index now surfaces two cross-cutting topics** that were only discoverable on the pages
  that implemented them: `clearArray`, and the fact that `ArrayPool<T>.Shared` trims itself under
  memory pressure while `DefaultObjectPool<T>` never does.
- **Cipher hard rules** in the cryptography porting guide now state the AEAD disposal contract. That
  was previously unstatable rather than merely absent — Ascon kept working after disposal while its
  four siblings threw.
- `Ntt.Barrett` input and output ranges are documented (#269).
