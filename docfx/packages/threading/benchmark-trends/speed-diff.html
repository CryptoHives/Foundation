CryptoHives Threading Speed Differences

How far apart competing implementations of the same synchronization primitive typically land, for the benchmark run selected below. Every cell's ratio is that variant's mean time divided by the fastest variant's mean time for the same primitive in that run — 1.00 is the winner, 2.00 means twice as slow. Both numbers come from the scenario closest to normal use - one contending party (not zero, and not a bare uncontended call some benchmark classes also record) with a live, uncancelled token where one was measured - rather than an average across every contention level a "Scaling by contention" chart would show: a "Multiple" benchmark's mean time at high contention is the time for many concurrent operations, not a per-operation cost, so blending it in would let whichever variant scales worst under load dominate the ratio.

† marks a "System" cell whose primitive may have no true async wait API (AutoResetEvent, ManualResetEvent, Barrier, ReaderWriterLockSlim) - its benchmark measures a blocking wait rather than an awaited one, so the ratio is a baseline reference rather than a fair race against the async implementations in the other columns. ‡ marks "ProtoPromise" - it builds on its own Promise/Promise<T> type and its own cancellation token rather than System.Threading.Tasks.ValueTask and CancellationToken, so it is not drop-in compatible with code written against the BCL types the other columns share.
