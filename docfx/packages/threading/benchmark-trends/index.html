CryptoHives Threading Benchmark Trends

Benchmark history for CryptoHives.Foundation.Threading's async synchronization primitives — how each one performs against reference libraries (Nito.AsyncEx, NeoSmart, ProtoPromise, Microsoft.VisualStudio.Threading), and against the synchronous BCL baselines they replace (lock/Monitor, SpinLock, Interlocked, ReaderWriterLockSlim, Barrier, CountdownEvent, ...) — across platforms and contention levels, and how that's changed over time as the code evolves. Pick a platform, primitive family, and operation below; every implementation is plotted as its own line so they're directly comparable at a glance. Where a benchmark varies by CancellationToken state, the Cancellation selector picks which state to plot (a live-but-unfired token adds overhead compared to CancellationToken.None, which is why it's kept as its own axis rather than doubling every legend entry). Runs entirely in your browser (no server, no external database) — see the hint below the chart for the two view modes.

Data source: benchmark-history.sqlite, generated at build time by scripts/threading-benchmark-trends/import_run_archive.py from the run archive on the benchmarks branch — so it is a derived artifact rather than a committed file, and any recorded run can be rebuilt from the archive at any time. Table (one run) is the default: it reproduces one run's report, every dimension that run carried as its own column, grouped and ordered as BenchmarkDotNet ordered it, with the baseline row highlighted and Ratio computed against it per parameter combination and cancellation state. Pick any recorded run rather than only the newest, and optionally a second one to compare against — two dates on one machine, or the same commit on two machines, which the run list marks as (same commit). The chart modes plot one point per recorded run; hover a point for the exact commit, value and the .NET runtime it was measured on. Trend over time plots every recorded parameter combination for the current filters at once (use the line-style legend below to hide ones you don't want). Scaling by contention plots the benchmark's parameterized axis on the X axis using each implementation's most recent run — usually queued waiters, but some benchmarks scale a different dimension (distinct keys or threads, for the keyed locks). Because that view spends its X axis on the parameter, the line-style channel is free, so it draws every cancellation state and both metrics at once — colour is the implementation, line style the cancellation state, and time is read off the left axis with allocation on the right. All three legends toggle. The Cancellation and Metric selectors above therefore apply to Trend over time only, where the parameter needs the line style and there is no channel left for them. Some methods aren't parameterized at all (e.g. a plain uncontended-only benchmark) — those show a single point per implementation in both views.
